# Evidence Freshness and Test Runner Profile Design

> Date: 2026-06-14
> Scope: `skills/e2e-dev-harness`
> Status: proposed design, pending implementation
> Related: `docs/superpowers/specs/2026-06-13-enterprise-style-profile-design.md`, `docs/superpowers/specs/2026-06-13-loop-engineering-truth-chain-closure-design.md`

## Executive Summary

The harness already requires `failing_tests`, `passing_tests`, and
`verification` to be genuine command evidence with the correct exit code. That
is the right baseline, but the `mini-agent` prompt-caching run exposed two gaps:

- command evidence proves that a command ran at a point in time, but it does not
  tell later phases whether the evidence still describes the current worktree;
- workers can invent ad hoc test aggregators in the target repository, which can
  blur the difference between feature-scoped RED tests, full regression tests,
  and harness helper scripts.

This design adds a small set of structured contracts around command evidence:

```text
start / clarified
  -> discover or declare the repository's test runner profile
  -> persist test-profile.json
red
  -> require command evidence plus red-failure-manifest.json
  -> bind evidence to git/diff/input hashes
implemented / verified
  -> show stale evidence warnings when source or tests changed after RED
  -> require current passing evidence for the selected suite scope
doctor / next
  -> report evidence freshness, suite scope, and runner provenance
```

The product decision is: command evidence remains the primitive, but it must be
bound to a repo snapshot and interpreted through a test-runner profile. Exit code
alone is not enough to determine whether a harness gate is meaningful.

## Problem Statement

In `mini-agent`, the RED worker produced `docs/agent-runs/.../red/failing_tests.json`
from:

```text
python tests/run_all.py
```

That artifact was valid command evidence: it was JSON, genuine, and had a
non-zero exit code. Later inspection found three important wrinkles:

- the repository uses self-executing Python test files, not pytest-style tests;
- `tests/run_all.py` was a feature test aggregator, not a true full-suite runner;
- after partial implementation, several tests passed, so the original RED output
  no longer described the current worktree even though it remained historically
  valid RED evidence.

The current harness can validate the shape and exit code of command evidence, but
it cannot express these distinctions.

## Current Checkout Facts

- Command evidence is generated by
  `skills/e2e-dev-harness/scripts/e2e_harness/adapters/evidence/command_evidence.py`.
- Evidence validation for `failing_tests`, `passing_tests`, and `verification`
  lives in
  `skills/e2e-dev-harness/scripts/e2e_harness/adapters/evidence/validate.py`.
- `COMMAND_KEYS` currently maps `failing_tests` to non-zero exit and
  `passing_tests` / `verification` to zero exit.
- `verification` is replay-protected through `REPLAY_KEYS`; `failing_tests` is
  currently historical command evidence and is not replayed.
- `submit_evidence` records artifact path, sha256, and bytes in run-state.
- Worker packets already carry `context_paths` and `expected_outputs`; this is
  the right seam for passing test profile artifacts to workers.
- The prior enterprise style-profile design already established the pattern:
  structured profile artifact, dispatch context inclusion, and evidence gate.

## Goals

- Preserve genuine command evidence as the source of truth for command execution.
- Make it clear whether evidence is historical or current for the worktree.
- Prevent feature-specific aggregators from being mistaken for full test suites.
- Let the harness recognize repo-specific test styles before RED workers write
  tests or runners.
- Keep generated harness helper scripts out of product test directories unless
  explicitly allowed.
- Ensure RED failures are tied to acceptance criteria and fail for the right
  reason, not because of missing files, import errors, or dependency drift.
- Surface stale evidence and runner-scope warnings in `doctor`, `next`, and gate
  failure messages.

## Non-Goals

- No attempt to replace project-native test frameworks.
- No requirement that every repository use pytest, npm, Maven, or any one runner.
- No automatic fixing of bad tests in the evidence validator.
- No mandatory replay of RED evidence after implementation; RED is historical by
  nature. The harness should label it rather than erase it.
- No runtime-adapter-specific policy logic.

## Design Overview

Add four additive artifacts:

```text
docs/agent-runs/<run>/test-profile.json
docs/agent-runs/<run>/red/red-failure-manifest.json
docs/agent-runs/<run>/generated-runners/<runner-name>
docs/agent-runs/<run>/evidence-index.json
```

And extend command evidence with snapshot metadata:

```json
{
  "schema": "e2e-dev-harness.command-evidence.v2",
  "command": "python docs/agent-runs/<run>/generated-runners/run_feature.py",
  "exit_code": 1,
  "cwd": "...",
  "git": {
    "head": "abc123",
    "dirty_tree_hash": "sha256:...",
    "tracked_input_hash": "sha256:..."
  },
  "suite": {
    "scope": "feature",
    "profile": "self-executing-python",
    "selected_tests": [
      "tests/test_cache_stats_parsing.py",
      "tests/test_cli_cache_line.py"
    ],
    "excluded_existing_tests": [
      "tests/test_streaming.py",
      "tests/test_subagent_team.py"
    ]
  },
  "phase": "RED",
  "historical": true
}
```

Version 1 evidence remains valid. Version 2 adds interpretation, not a breaking
replacement.

## Test Profile Contract

`test-profile.json` describes the repository's testing style and safe runner
commands.

```json
{
  "schema": "e2e-dev-harness.test-profile.v1",
  "profile_id": "mini-agent-self-executing-python",
  "detected_from": [
    "tests/test_streaming.py",
    "tests/test_subagent_team.py",
    "pyproject.toml"
  ],
  "runner_style": "self-executing-python",
  "commands": {
    "single_test": "python {path}",
    "feature_suite": "python docs/agent-runs/{run_id}/generated-runners/run_feature.py",
    "full_suite": "python docs/agent-runs/{run_id}/generated-runners/run_full.py"
  },
  "generated_runner": {
    "allowed": true,
    "preferred_directory": "docs/agent-runs/{run_id}/generated-runners",
    "may_write_to_tests": false
  },
  "suite_policy": {
    "red_required_scope": "feature",
    "verified_required_scope": "feature",
    "high_tier_verified_required_scope": "full"
  }
}
```

### Runner Styles

Initial runner styles:

- `self-executing-python`: test files are executable scripts with their own
  `main()` and `sys.exit(...)`.
- `pytest`: use `python -m pytest ...` or project pytest command.
- `unittest`: use `python -m unittest ...`.
- `npm`: use `npm test` or `npm run test`.
- `maven`: use `mvn test`.
- `gradle`: use `gradle test` or `./gradlew test`.
- `custom`: explicit project-local command only.

The style is not merely advisory. It controls what RED and verification workers
may use for command evidence.

## Evidence Snapshot Metadata

Extend `record_command` to collect cheap, best-effort snapshot data:

- `git.head`: `git rev-parse HEAD`, when available.
- `git.status_porcelain_hash`: hash of `git status --porcelain=v1`.
- `git.diff_hash`: hash of `git diff --binary` plus staged diff.
- `inputs`: explicit paths supplied by the caller, with per-file sha256.
- `suite.scope`: `feature`, `full`, `manual-e2e`, or `smoke`.
- `suite.selected_tests`: tests the command is expected to run.
- `suite.generated_runner_path`: runner artifact path, when present.

The validator should not fail only because git metadata is unavailable. It should
record `git.available=false` and let doctor report reduced confidence.

## Suite Scope Semantics

Evidence needs a scope label:

- `feature`: tests written or selected for this acceptance contract.
- `full`: the repository's full automated test suite.
- `smoke`: a smaller project-defined smoke suite.
- `manual-e2e`: manual or externally configured end-to-end validation.

Phase rules:

| Phase | Required Evidence | Scope Rule |
| --- | --- | --- |
| RED | `failing_tests` + `red_failure_manifest` | `feature` is enough |
| IMPLEMENTED | `passing_tests` | same feature scope as RED |
| VERIFIED minimal | `verification` | feature scope is enough unless pipeline says otherwise |
| VERIFIED critical/audited | `verification` | prefer `full`; allow feature only with explicit scope manifest |

This preserves fast local TDD while making limited verification honest.

## RED Failure Manifest

`red_failure_manifest` prevents "exit 1" from being the only proof that RED is
meaningful.

```json
{
  "schema": "e2e-dev-harness.red-failure-manifest.v1",
  "command_evidence": "docs/agent-runs/<run>/red/failing_tests.json",
  "items": [
    {
      "acceptance_id": "AC-004",
      "test": "tests/test_cli_cache_line.py",
      "expected_failure_kind": "missing_observability_event",
      "observed_failure_signature": "cache_stats events emitted: 0",
      "right_reason": true
    }
  ],
  "infrastructure_failures": []
}
```

Validation rules:

- every acceptance item that is supposed to be covered by RED has at least one
  failure item;
- `infrastructure_failures` must be empty unless the worker submits a blocked
  status instead of done;
- observed failure signatures must be present in command evidence stdout or
  stderr tail, or in a referenced full-output artifact;
- if any failure is marked `right_reason=false`, RED does not pass.

This is deliberately lightweight. It does not need to understand every assertion;
it only prevents opaque non-zero exits.

## Generated Runner Policy

Generated runners should be artifacts first, product files only by exception.

Preferred location:

```text
docs/agent-runs/<run>/generated-runners/run_feature.py
```

Allowed target-repo writes:

- only when `test-profile.json.generated_runner.may_write_to_tests == true`;
- runner name must make scope explicit, for example `run_prompt_caching_tests.py`
  rather than `run_all.py`;
- generated runner must fail if any selected test path is missing;
- generated runner must list selected tests in deterministic order.

This keeps harness plumbing from silently becoming product code.

## Freshness Evaluation

Add a pure freshness check that compares command evidence metadata to current
repo state.

```text
fresh       same head, same diff hash, same input hashes
historical  intentionally old evidence for an earlier phase, still valid history
stale       evidence claims current relevance but source/tests changed
unknown     metadata unavailable
```

RED evidence is normally `historical` after implementation begins. That should
not invalidate RED. It should affect presentation:

```text
RED evidence: historical, recorded before 9 source/test file changes.
Current verification evidence: missing.
```

`passing_tests` and `verification` should be `fresh` or explicitly justified as
`manual-e2e` / `external`.

## Gate Changes

### New Structured Keys

Extend `STRUCTURED_KEYS` with:

- `test_profile`
- `red_failure_manifest`
- `evidence_index`

Extend pipeline phase gates:

- `CLARIFIED`: optionally include `test_profile` when auto-detected or explicit.
- `RED`: require `failing_tests` and `red_failure_manifest`.
- `VERIFIED`: require current `verification`; high tiers can require full-scope
  verification.

### Command Evidence Validation

Keep existing checks:

- JSON parse
- command evidence schema
- genuine record structure
- expected exit code
- verification replay allowlist

Add optional v2 checks:

- `suite.scope` is valid;
- selected tests are non-empty for feature scope;
- generated runner path, if present, is under an allowed directory;
- `failing_tests` with `suite.scope=full` cannot use a runner that excludes known
  tracked test files without declaring them;
- `passing_tests` / `verification` with stale metadata returns a freshness reason
  that can block or warn depending on phase policy.

## Dispatch Changes

`dispatch` and `BuiltinAgentTeamProvider` already pass `context_paths` into
worker packets. Add the test profile and current evidence index there:

```json
{
  "context_paths": [
    "docs/agent-runs/<run>/run-state.json",
    "docs/agent-runs/<run>/test-profile.json",
    "docs/agent-runs/<run>/evidence-index.json"
  ],
  "expected_outputs": [
    "failing_tests",
    "red_failure_manifest"
  ]
}
```

Runtime adapters remain simple. They should render the extra paths in prompts
but should not interpret test policy.

## CLI and Doctor Output

`doctor state` should include:

```text
Evidence freshness:
  RED failing_tests: historical, feature scope, recorded at HEAD abc123
  RED red_failure_manifest: covers AC-001..AC-007, 0 infrastructure failures
  VERIFIED verification: missing

Runner profile:
  style: self-executing-python
  feature runner: docs/agent-runs/<run>/generated-runners/run_feature.py
  full runner: not recorded
```

When a generated runner is inside `tests/`, doctor should warn unless the profile
explicitly permits it.

## Migration Plan

1. Add `test-profile.json` generation with a conservative detector.
2. Extend command evidence schema to v2 while accepting v1.
3. Add `red_failure_manifest` validator and gate it behind a feature flag or new
   pipeline version.
4. Move generated runner guidance into RED worker packets.
5. Add doctor freshness reporting.
6. Turn stale verification from warning into blocker for strict pipelines.
7. Update existing tests for command evidence and navigation.

## Acceptance Criteria

- A self-executing Python repository receives a `test-profile.json` that does
  not force pytest.
- RED command evidence can be marked historical after implementation without
  invalidating the RED phase.
- `passing_tests` or `verification` evidence recorded before source/test changes
  is reported as stale.
- A feature runner named `run_all.py` that excludes existing tracked tests is
  reported as misleading unless suite scope is explicitly `feature`.
- A generated runner under `docs/agent-runs/<run>/generated-runners/` is accepted.
- A generated runner under `tests/` is accepted only when the profile allows it.
- RED does not pass when command evidence is non-zero solely because of an
  infrastructure failure listed in `red_failure_manifest`.
- Worker packets include the test profile path before RED workers produce tests.

## Open Questions

- Should `red_failure_manifest` be mandatory for `minimal`, or only for
  `standard` and above during rollout?
- Should full-suite verification be required for all `critical` runs, or only
  when the detected test profile has a reliable full-suite command?
- Should stale verification block immediately, or should it first appear as a
  doctor warning for one release?
- How much git metadata should command evidence collect in repositories with very
  large diffs?

## Recommended First Slice

Implement the smallest slice that would have made the `mini-agent` run clearer:

1. Generate `test-profile.json` for self-executing Python repositories.
2. Store generated feature runners under `docs/agent-runs/<run>/generated-runners`.
3. Add `suite.scope` and git snapshot metadata to new command evidence.
4. Add doctor output that says RED evidence is historical and verification is
   current or stale.

This first slice avoids changing core lifecycle semantics while improving the
truthfulness of every later gate.
